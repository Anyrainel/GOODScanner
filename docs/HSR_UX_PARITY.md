# 原神与星穹铁道的桌面体验对照

检查日期：2026-10-08。以下结论来自当前 GOODScanner 与 GGStarRail 源码，
描述实现状态；自动测试通过不代表实机游戏操作已验证。

## 管理器的完成范围

星铁已有本地管理执行链路，但没有完成与原神相同的网页连接体验。

- 桌面端 `application/src/gui/star_rail_manager_tab.rs` 选择指令文件，
  重扫库存、生成精确预览，再要求复核与逐类授权。
- `application/src/gui/star_rail_worker.rs` 的 `spawn_manager_preview` 与
  `spawn_manager_apply` 调用实际扫描器和 `apply_manager_envelope`。
  后者包含重新核对库存、匹配、执行、验证，以及中断恢复日志。
  因此并非仅有静态界面或只生成文件的占位功能。
- 星铁没有 HTTP 管理服务器、端口配置、网页连接状态或任务查询接口。
  原神的 `genshin/src/server.rs` 已提供 `/manage`、`/equip`、`/scan`、
  `/status`、`/result` 和分类数据查询。
- GGStarRail 的 `src/pages/account-data/TriageView.tsx` 通过
  `downloadPreview` 下载 JSON；`src/lib/managerInstructions.ts` 定义指令格式。
  目前没有将指令发送到桌面程序并查询结果的客户端。

这说明文件工作流是桌面端与网页端共同采用的实现路线，不是 egui 的限制，
也不是星铁协议要求必须通过文件操作。

## 体验差异

| 项目 | 原神 | 星铁现状 | 判断与本轮处理 |
| --- | --- | --- | --- |
| 管理器入口 | 启动连接，网站发送请求 | 选文件、重扫预览、复核、逐类授权、应用 | 未对齐；HTTP 与网页客户端仍需实现 |
| 请求状态 | 等待请求，按请求类型、数量显示进度和结果 | 本地预览/应用的进度，无法等待网页请求 | 未对齐；不能只改“等待指令文件”的文案来假装已连接 |
| 文件与恢复细节 | 常规流程不要求选择恢复日志或核对摘要 | 日志路径、摘要、精确 JSON 和多项复核均暴露在常规界面 | 不必要的操作负担；恢复记录可以由程序管理，技术细节可放在高级区域 |
| 结果回传 | 网页可查询任务结果与扫描数据 | 本地完成提示，没有网页回传接口 | 未对齐；需要服务端与网页共同实现 |
| 管理操作范围 | 加解锁、装备/卸下、远程扫描 | 本地锁定/解锁、弃置/取消弃置；网站生成的指令范围更小，没有装备流程 | 弃置是合理游戏差异；装备与远程扫描属于功能缺口 |
| 导出位置 | 默认程序目录，不要求选择目录 | 原来在抓包与扫描页重复提供目录选择 | 本轮移除选择控件与“必须选目录”的门槛；未设置目录时使用程序目录，已有自定义保存位置继续有效 |
| 扫描的导出策略 | 可仅保留最新导出，也可停止时保存已有结果 | 扫描始终新建导出；用户中止时返回未导出 | 未对齐；应增加同样的用户选择，并验证部分结果的覆盖状态 |
| 抓包的导出策略 | 仅保留最新导出默认开启 | 有同样选项，但默认关闭 | 默认策略仍有差异；本轮不改写用户保存的选择 |
| 抓包帮助 | 原来在左侧集中展示使用说明 | 原来有另一份左侧说明 | 本轮两边移除，改用共享状态文案：关闭游戏、准备、登录、等待数据、打开成就、导出、停止和失败 |
| 管理器的 HDR 与延迟设置 | 在管理器页可直接调整 | 使用扫描页的共享设置，管理器页没有同样入口 | 未对齐；应复用设置组件，让同一配置在相关页面都可访问 |

两边已经共用窗口、游戏切换、语言、布局分割、日志、错误提示、任务行、
数据刷新与部分工作线程封装。问题主要在管理器的传输层和操作流程，
不是所有实现都互不关联。

## 合理的游戏差异

光锥、遗器与位面饰品、开拓者昵称与性别、行迹、星魂、叠影、弃置标记，
以及各自的界面坐标、网络端口、协议、匹配字段和导出格式需要保留。
HSR-Scanner v4 与原神 GOOD 的数据结构不同，不应为了界面一致而混用数据模型。

## 管理器对齐后的产品流程

1. 桌面端显示连接设置和“启动连接”；启动后显示“在 GGArtifact 中连接管理器”。
2. 网页发送请求；桌面端显示请求类型、数量及实际处理步骤。
3. 扫描、匹配、执行与验证继续使用现有星铁实现。恢复记录自动管理，
   需要用户处理的歧义、失败和恢复情况才进入主要界面。
4. 网页查询任务状态并取得结果；可以在网页完成请求复核，避免桌面重复展示摘要和 JSON。
5. 停止、重试、并发请求、程序重启后的恢复、跨游戏请求，以及库存结果回传
   都需要通过协议集成测试，最后再进行实机验证。

不能只在桌面增加一个 HTTP 监听器就宣称联动完成：还需要 GGStarRail 的
连接入口、发送/查询客户端、请求版本与游戏标识，以及明确的结果与错误处理。
